## Masalahnya bukan hanya response yang lambat

Route Handler sering menjadi perantara antara browser dan API lain. Browser meminta `/api/search`, lalu server meneruskan query itu ke layanan katalog, database HTTP, atau API pihak ketiga. Kalau pengguna mengetik cepat atau berpindah halaman, request pertama mungkin sudah tidak dibutuhkan lagi. Namun proses di server bisa tetap berjalan sampai `fetch` selesai.

Akibatnya, server membayar pekerjaan untuk response yang tidak akan pernah dibaca. Pada trafik kecil, ini mungkin tidak terasa. Pada endpoint yang memanggil beberapa layanan atau menunggu response lambat, request yang sudah ditinggalkan dapat menumpuk dan memakai koneksi serta slot kerja yang seharusnya dipakai request aktif.

`AbortController` memberi cara standar untuk membatalkan pekerjaan async yang mendukung `AbortSignal`. Di Route Handler Next.js, signal dari objek `Request` bisa diteruskan ke `fetch`.

## Teruskan `request.signal` ke fetch

Contoh sederhana dengan App Router:

```ts
// app/api/search/route.ts
import { NextRequest, NextResponse } from "next/server";

export async function GET(request: NextRequest) {
  const query = request.nextUrl.searchParams.get("q")?.trim();

  if (!query) {
    return NextResponse.json({ items: [] });
  }

  const upstream = await fetch(
    `https://catalog.example.com/search?q=${encodeURIComponent(query)}`,
    {
      signal: request.signal,
      headers: {
        accept: "application/json",
      },
    },
  );

  if (!upstream.ok) {
    return NextResponse.json(
      { error: "Layanan katalog gagal merespons" },
      { status: 502 },
    );
  }

  return NextResponse.json(await upstream.json());
}
```

`request.signal` akan berstatus aborted ketika request asal tidak lagi tersedia. Dengan meneruskannya ke `fetch`, runtime punya kesempatan menghentikan request upstream juga. Tanpa opsi `signal`, `fetch` tidak tahu bahwa hasilnya sudah tidak diperlukan.

Ini bukan pengganti timeout. Client bisa tetap terhubung sementara layanan upstream macet, jadi endpoint tetap perlu batas waktu sendiri.

## Gabungkan dengan timeout

Buat signal yang membatalkan request karena salah satu dari dua hal: client terputus atau batas waktu tercapai. `AbortSignal.any()` menggabungkan beberapa signal, sedangkan `AbortSignal.timeout()` membuat signal yang otomatis batal setelah durasi tertentu.

```ts
function withTimeout(
  requestSignal: AbortSignal,
  milliseconds: number,
) {
  return AbortSignal.any([
    requestSignal,
    AbortSignal.timeout(milliseconds),
  ]);
}

export async function GET(request: NextRequest) {
  const signal = withTimeout(request.signal, 3_000);

  try {
    const response = await fetch("https://catalog.example.com/items", {
      signal,
    });

    if (!response.ok) {
      return NextResponse.json(
        { error: "Upstream mengembalikan error" },
        { status: 502 },
      );
    }

    return NextResponse.json(await response.json());
  } catch (error) {
    if (error instanceof Error && error.name === "TimeoutError") {
      return NextResponse.json(
        { error: "Upstream terlalu lambat" },
        { status: 504 },
      );
    }

    if (error instanceof Error && error.name === "AbortError") {
      // Request client berakhir. Tidak ada response yang perlu dikirim.
      return new Response(null, { status: 499 });
    }

    throw error;
  }
}
```

Status `499` bukan status HTTP resmi. Nginx dan beberapa sistem proxy memakainya untuk mencatat client closed request. Kamu bisa memilih status lain sesuai kontrak aplikasi atau membiarkan error tersebut ditangani oleh platform. Yang penting, jangan menganggap semua abort sebagai kegagalan upstream yang harus dicatat sebagai error aplikasi.

## Batalkan semua pekerjaan turunan

Meneruskan signal hanya ke fetch pertama belum cukup jika handler menjalankan beberapa operasi berurutan. Parser atau fungsi pembantu yang melakukan pekerjaan async juga perlu menerima signal dan memeriksanya pada titik yang tepat.

```ts
async function loadRecommendations(
  userId: string,
  signal: AbortSignal,
) {
  const response = await fetch(
    `https://recommendation.example.com/users/${userId}`,
    { signal },
  );

  const data = await response.json();
  signal.throwIfAborted();

  return data.items;
}
```

`signal.throwIfAborted()` berguna setelah operasi yang tidak menerima signal secara langsung, misalnya setelah parsing atau sebelum memulai pekerjaan CPU yang mahal. Untuk loop besar, cek signal di dalam loop atau pecah pekerjaan menjadi unit yang bisa dibatalkan. Abort tidak dapat secara ajaib menghentikan fungsi sinkron yang sedang memakai CPU.

## Bedakan abort dari error biasa

Abort adalah alur normal pada endpoint yang dipanggil dari UI interaktif. Pengguna mengetik `rea`, lalu `reac`, lalu `react`; request untuk `rea` memang boleh berakhir di tengah jalan. Logging semua `AbortError` sebagai error produksi akan membuat metrik terlihat lebih buruk daripada kondisi sebenarnya.

Sebaliknya, timeout perlu dicatat sebagai masalah dependensi atau kapasitas. Bedakan keduanya di blok `catch`, lalu ukur frekuensinya. Jika timeout sering terjadi, memperpanjang timeout biasanya hanya menunda masalah. Periksa latency upstream, jumlah koneksi, dan apakah hasil yang sama bisa di-cache.

## Batasan runtime dan pengujian

Dukungan pembatalan bergantung pada runtime dan library yang dipakai. `fetch` bawaan runtime modern mendukung `AbortSignal`, tetapi client database atau SDK pihak ketiga belum tentu meneruskannya. Periksa dokumentasi SDK sebelum menambahkan opsi yang hanya terlihat benar tetapi diabaikan.

Uji dua jalur: upstream selesai sebelum timeout, dan upstream dibatalkan setelah signal dipicu. Untuk pengujian Route Handler, gunakan server mock yang menunda response. Pastikan test juga memeriksa bahwa handler tidak mengubah abort menjadi response error generik secara keliru.

Pola praktisnya sederhana: gunakan `request.signal` sebagai sumber pembatalan, gabungkan dengan timeout yang masuk akal, lalu teruskan signal ke setiap operasi yang mendukungnya. Hasilnya bukan sekadar response lebih cepat, tetapi pekerjaan server yang lebih cepat berhenti saat sudah tidak punya pemakai.

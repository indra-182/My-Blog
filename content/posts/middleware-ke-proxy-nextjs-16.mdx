## Kenapa middleware diganti nama

Jika kamu mengikuti perkembangan Next.js, istilah `middleware` terasa familiar — terlalu familiar. Namanya sama dengan middleware Express.js, dan itu sumber kebingungan yang berkelanjutan. Developer sering mengira proxy berperilaku seperti middleware Express: eksekusi berurutan di dalam proses aplikasi, bisa sharing state, melempar error ke handler berikutnya. Padahal perilakunya jauh berbeda — ia berjalan di lapisan network, sebelum request masuk ke aplikasi.

Next.js 16 merespons kebingungan ini dengan merombak istilah sekaligus menyempitkan cakupan: file convention `middleware.ts` di-deprecate dan diganti menjadi `proxy.ts`. Namanya lebih jujur. Proxy adalah gerbang network di depan aplikasi — bukan bagian dari aplikasi itu sendiri. Perubahan ini juga sinyal arah framework: Next.js ingin developer mengurangi ketergantungan pada proxy, dan menyediakan API yang lebih ergonomis untuk kebutuhan yang sebelumnya dipaksakan lewat middleware.

## Apa yang berubah secara teknis

Secara mekanisme, tidak banyak yang berubah dari v15 ke v16 — yang berubah adalah nama file, nama fungsi, dan default runtime.

- File `middleware.ts` di rename menjadi `proxy.ts` (lokasi tetap di root project atau dalam folder `src/`, sejajar dengan `app/`).
- Export `middleware` menjadi `proxy` (bisa juga default export).
- Default runtime berubah dari Edge menjadi Node.js.
- Konfigurasi `matcher` tetap sama persis.

Contoh paling sederhana: redirect semua request ke halaman `/about` menuju `/home`.

```ts
// proxy.ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function proxy(request: NextRequest) {
  return NextResponse.redirect(new URL("/home", request.url));
}

export const config = {
  matcher: "/about/:path*",
};
```

Fungsi `proxy` menerima `NextRequest` dan bisa mengembalikan `NextResponse` — redirect, rewrite, atau langsung `Response.json()` jika ingin memotong request. `config.matcher` menentukan path mana yang dilalui proxy, dan nilainya harus konstanta agar bisa dianalisis saat build.

Migrasi dari project lama cukup dijalankan satu perintah:

```bash
npx @next/codemod@canary middleware-to-proxy .
```

Codemod ini merename file dan mengganti nama fungsi `middleware` menjadi `proxy`. Setelah itu, periksa kembali matcher dan logika di dalamnya — perilaku runtime yang berbeda (Node.js vs Edge) bisa berdampak pada kode yang sebelumnya mengasumsikan Edge runtime, misalnya penggunaan API Node tertentu kini justru bekerja lebih leluasa.

## Studi kasus: proteksi halaman dashboard

Kasus paling umum proxy dipakai adalah auth check. Logikanya: jika session tidak valid dan user mengakses halaman terproteksi, redirect ke halaman login.

```ts
// proxy.ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";
import { getSession } from "@/lib/session";

export async function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl;
  const session = await getSession(request);

  const isProtected = pathname.startsWith("/dashboard");
  if (isProtected && !session) {
    const loginUrl = new URL("/login", request.url);
    loginUrl.searchParams.set("next", pathname);
    return NextResponse.redirect(loginUrl);
  }

  // User sudah login tapi mengunjungi /login — arahkan balik
  if (pathname.startsWith("/login") && session) {
    return NextResponse.redirect(new URL("/dashboard", request.url));
  }

  return NextResponse.next();
}

export const config = {
  // Lewati aset statis agar CSS/JS/gambar tidak diblokir
  matcher: [
    "/((?!api|_next/static|_next/image|favicon.ico|sitemap.xml|robots.txt).*)",
  ],
};
```

Pola matcher negatif di atas penting. Tanpa matcher, proxy jalan untuk **setiap** request, termasuk `_next/static`, `_next/image`, dan file di `public/`. Logika auth yang tidak hati-hati bisa secara tidak sengaja memblokir CSS dan JavaScript aplikasi sendiri, yang gejalanya gawat dan sulit dilacak: halaman tampil tanpa styling.

## Membaca dan menulis cookies

Cookies pada dasarnya adalah header. Di request, ia hidup di header `Cookie`; di response, di `Set-Cookie`. `NextRequest` dan `NextResponse` membungkus keduanya dengan API yang nyaman:

```ts
// proxy.ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function proxy(request: NextRequest) {
  // Baca cookie dari request
  const theme = request.cookies.get("theme")?.value;
  const hasSession = request.cookies.has("session");

  if (!hasSession) {
    request.cookies.delete("session");
  }

  // Set cookie pada response
  const response = NextResponse.next();
  response.cookies.set("theme", theme ?? "light", { path: "/" });
  return response;
}
```

Catatan penting: mutasi `request.cookies` hanya mengubah apa yang terlihat oleh proxy itu sendiri — untuk meneruskan cookie baru ke aplikasi, set lewat `NextResponse.next({ request: { headers } })` atau langsung pada response cookies seperti contoh di atas.

## Dua perangkap yang sering bikin sakit kepala

**1. Proxy bukan pengganti auth di Server Action.** Server Function tidak dianggap sebagai rute terpisah dalam rantai eksekusi — ia POST ke rute tempat ia dipakai. Kalau matcher mengecualikan path itu (misalnya karena halaman publik), Server Action di path yang sama ikut tidak diproteksi. Selalu verifikasi otorisasi di dalam setiap Server Action, jangan hanya mengandalkan proxy.

**2. Jangan taruh logika berat di proxy.** Proxy dijalankan terpisah dari kode render, dan pada platform tertentu dideploy ke CDN agar redirect/rewrite berjalan cepat. Kode yang bergantung pada shared module atau global state akan bermasalah di situ. Untuk passing data dari proxy ke aplikasi, gunakan header, cookies, rewrite, atau URL — bukan modul bersama.

## Kapan sebaiknya tidak memakai proxy sama sekali

Nama baru ini sekaligus pengingat: proxy adalah **pilihan terakhir**. Banyak kebutuhan yang dulu "dipaksakan" lewat middleware kini punya API yang lebih tepat:

- **Redirect & rewrite statis** — cukup `redirects` dan `rewrites` di `next.config.ts`. Keduanya dievaluasi sebelum proxy dan tidak menambah biaya runtime.
- **Response headers global** — konfigurasi `headers` di `next.config.ts`.
- **Auth di halaman** — validasi di Server Component atau layout, dengan `redirect()` langsung dari sana.
- **CORS per rute** — Route Handler punya opsi konfigurasi CORS sendiri.

Gunakan proxy hanya untuk yang benar-benar butuh inspeksi request sebelum routing: redirect berbasis kondisi kompleks, rewrite A/B test, blokir IP/region, atau proteksi path API lama yang belum sempat dimigrasi.

## Kesimpulan

Perubahan `middleware` ke `proxy` di Next.js 16 sebagian besar bersifat kosmetik — mekanisme lama tetap berfungsi, dan codemod resmi menyelesaikan migrasi dalam satu perintah. Yang lebih penting adalah perubahan mental model: proxy adalah network boundary di depan aplikasi, bukan middleware Express, dan harus dipakai seminimal mungkin. Saat upgrade ke Next.js 16, jalankan codemod, periksa default runtime Node.js yang baru, tinjau ulang setiap penggunaan proxy — lalu tanyakan pada diri sendiri: apakah kebutuhan ini bisa diselesaikan dengan API yang lebih sederhana di `next.config.ts` atau langsung di Server Component?
